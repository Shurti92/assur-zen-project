# Contrat d'interface — Internationalisation (i18n) de l'application

> ✅ **`GET /i18n/{langueCode}` est en ligne** (constaté le 2026-08-06, répond `200 {}` pour `FR`/`EN` — dictionnaire vide pour l'instant, à peupler). Le frontend est déjà branché dessus (`core/i18n/transloco-loader.ts`) et fusionne cette réponse avec un dictionnaire de secours local le temps que le dictionnaire backend se remplisse — aucune régression pendant la transition.
>
> ⚠️ **Point d'attention important avant d'implémenter le paramètre `scope`** (§3 et §5) : voir l'encart "Format des clés avec `scope`" plus bas — l'implémentation actuelle du frontend (module Sinistres, déjà livré) impose un format précis pour que le `scope` fonctionne, différent de l'exemple générique donné plus bas dans ce document à l'origine.
>
> Suivi dans la mémoire projet "dépendances backend manquantes".

Base URL gateway : `https://localhost:9190/api-assur-zen` (via proxy `/api-assur-zen` en dev).

## 1. Contexte

L'objectif est de rendre toute l'interface Angular multilingue, avec changement de langue **instantané, sans rechargement de page**. Ça exclut l'i18n "build-time" d'Angular (`@angular/localize`, non utilisé aujourd'hui dans le projet — une seule occurrence orpheline dans `views/dashboard/routes.ts`), qui nécessite un build séparé par langue et donc un rechargement complet.

L'architecture retenue côté frontend est une i18n **runtime**, où les textes de l'interface sont chargés dynamiquement en fonction de la langue active et affichés via un pipe/directive réactif (`| transloco` ou équivalent) — changer la langue ne fait que rafraîchir le contenu déjà à l'écran, aucune navigation.

Ça déplace le dictionnaire de traductions hors du code source Angular (pas de fichiers JSON figés par build) et vers le backend, pour permettre :
- une mise à jour des traductions sans redéploiement frontend,
- une éventuelle administration des traductions par un non-développeur,
- une seule source de vérité, cohérente avec le reste de l'architecture (tout le référentiel métier est déjà piloté par API).

## 2. Ce qui existe déjà (rien à changer)

```
GET /api-assur-zen/langues
→ [{ id, code, libelle, active }]
```
Continue à peupler le sélecteur de langue. Le `code` (ex: `FR`, `EN`, `ES`, `RU`) devient la clé utilisée par le dictionnaire de traductions ci-dessous.

## 3. Proposition — dictionnaire de traductions (indispensable)

```
GET /api-assur-zen/i18n/{langueCode}?scope={scope}
```

| Paramètre | Type | Requis | Détail |
|---|---|---|---|
| `langueCode` | string (path) | oui | Doit correspondre à un `code` de `/langues` (ex: `FR`) |
| `scope` | string (query) | non | Regroupement fonctionnel des clés (voir §5). Si omis, retourne tout le dictionnaire de la langue. |

### Réponse `200` proposée

Objet plat clé → valeur (format directement consommable par les libs d'i18n runtime Angular, sans transformation) :

```json
{
  "common.actions.save": "Enregistrer",
  "common.actions.cancel": "Annuler",
  "sinistres.liste.titre": "Liste des sinistres",
  "sinistres.liste.rechercher": "Rechercher un sinistre, un assuré, une police…",
  "reclamations.statut.NOUVELLE": "Nouvelle",
  "reclamations.statut.EN_COURS": "En cours"
}
```

Points d'attention pour le backend :
- Les clés à interpolation (ex. `"Bonjour {{prenom}}"`) doivent conserver leurs placeholders tels quels — l'interpolation se fait côté frontend, pas côté backend.
- Pas de HTML dans les valeurs sauf cas justifié (le frontend traite le texte comme non-HTML par défaut, pour éviter tout risque d'injection).
- Encodage UTF-8 impératif (accents, caractères spéciaux du français, du russe en particulier).

> **⚠️ Format des clés quand `scope` est fourni — corrige l'exemple ci-dessus.**
> L'exemple JSON plus haut montre des clés déjà préfixées par leur module (`"sinistres.liste.titre"`). C'est correct **uniquement pour l'appel sans `scope`** (dictionnaire racine, ex. `common`). **Dès que `scope=sinistres` est passé en paramètre, la réponse ne doit PAS répéter `sinistres.` dans ses clés** :
> ```
> GET /i18n/FR?scope=sinistres
> → { "fields.assure": "Assuré", "liste.titre": "Liste des sinistres", "status.declare": "Déclaré", ... }
> ```
> C'est le comportement natif de la librairie frontend (Transloco) : elle imbrique automatiquement tout le contenu reçu sous le nom du `scope` demandé. Si le backend renvoie des clés déjà préfixées (`"sinistres.fields.assure"`), le résultat final devient `sinistres.sinistres.fields.assure` côté frontend — la traduction ne se résout jamais et l'app affiche la clé brute à l'écran. Confirmé en le testant en direct : le module Sinistres (déjà livré, `src/assets/i18n/{lang}/sinistres.json`) suit cette convention non-préfixée pour tous ses appels `scope=sinistres` — merci de répliquer exactement le même découpage de clés côté backend pour que la bascule du fichier local vers l'API se fasse sans aucune casse.

### Cache / performance (recommandé)

```
GET /api-assur-zen/i18n/version
→ { "FR": "2026-08-06T10:00:00Z", "EN": "2026-08-01T09:00:00Z", ... }
```
Un timestamp de dernière modification par langue, pour que le frontend sache s'il peut servir sa copie en cache local (`localStorage`) sans re-télécharger tout le dictionnaire à chaque session. Alternative acceptable : un simple header `Last-Modified`/`ETag` sur `GET /i18n/{langueCode}`.

## 4. Proposition — administration des traductions (recommandé, pas bloquant)

Sans ça, toute nouvelle clé ou correction de traduction nécessite un déploiement backend (migration de données). Avec ça, une page d'administration frontend devient possible.

```
GET    /api-assur-zen/i18n/entries?langueCode=&scope=&page=&size=
POST   /api-assur-zen/i18n/entries        { cle, scope, langueCode, valeur }
PUT    /api-assur-zen/i18n/entries/{id}   { valeur }
DELETE /api-assur-zen/i18n/entries/{id}
```

Modèle suggéré :

```
TraductionResponse {
  id: number,
  cle: string,          // ex: "sinistres.liste.titre"
  scope: string,        // ex: "sinistres"
  langueCode: string,   // ex: "FR"
  valeur: string,
  lastUpdate: string
}
```

## 5. Découpage par `scope` (pour le lazy-loading)

Le frontend est déjà organisé en modules fonctionnels lazy-loadés (`views/sinistres`, `views/reclamations`, `views/contrats`, etc.). Pour éviter de télécharger tout le dictionnaire d'un coup, chaque module ne charge que son `scope` + un scope `common` partagé (boutons, labels génériques, messages d'erreur transverses). Proposition de découpage initial, à affiner avec le backend :

`common`, `auth`, `dashboard`, `souscription`, `contrats`, `sinistres`, `assures`, `comptabilite`, `partenaires`, `fidelisation`, `satisfaction`, `configuration`, `monitoring`, `interceptors`.

## 6. Préférence de langue utilisateur (optionnel)

Ajouter un champ à `ProfileDetails`/`ProfileResponse` (`core/profile/models/profile-details.model.ts`) :

```
langueCode: string  // ex: "FR" — mis à jour via PUT /profiles/{id} existant
```

Sans ce champ, le choix de langue reste local au navigateur (`localStorage`) — fonctionnel, mais perdu si l'utilisateur change de poste ou vide son cache. Recommandé pour une vraie expérience multi-poste, non bloquant pour un premier lot.
